Nivel 1

Business Domain — el área grande del negocio

El Domain es la agrupación más amplia y estable. No describe todavía un flujo ni una pantalla: define el territorio funcional dentro del cual viven distintos procesos de negocio.

En nuestro caso, el dominio puede pensarse como DOM-RMA. Allí conviven todas las capacidades que pertenecen al mundo operativo de RMA. Hoy el proceso de Reparaciones es el que está modelado y aprobado, pero ya sabemos que más adelante deberán incorporarse también las ventas mayoristas de repuestos y las compras de repuestos.

Este nivel evita que el sistema quede conceptualmente limitado a “la app de reparaciones”. Desde el inicio asumimos que RMA será un dominio más amplio con varios procesos relacionados entre sí.

Ejemplo
DOM-RMA
├── PROC-REP  Gestión de Órdenes de Reparación
├── PROC-VTA  Gestión de Ventas de Repuestos
└── PROC-COM  Gestión de Compras de Repuestos
Pregunta que responde este nivel: ¿En qué gran área del negocio estamos trabajando?
Domain = agrupación funcional superior02
Nivel 2

Business Process — cómo ocurre realmente el negocio

El Business Process describe un flujo end-to-end del negocio. Acá todavía estamos mirando qué sucede en la operación real, independientemente de cómo se programe después.

Por ejemplo, PROC-REP representa la Gestión de Órdenes de Reparación. Dentro de ese proceso aparecen los eventos, decisiones, actividades, actores, reglas y caminos que llevan una orden desde que surge la necesidad hasta que se entrega el equipo o finaliza el circuito correspondiente.

Otro proceso futuro, como Compras de Repuestos, tendrá su propio flujo. Puede compartir conceptos con Reparaciones, como inventario o proveedores, pero seguirá siendo un proceso diferente porque responde a otro recorrido de negocio.

Ejemplo simplificado
Necesidad de reparación
→ Registrar cliente/equipo
→ Crear OR
→ Definir reparación
→ Validar recursos
→ Ingresar a cola
→ Reparar
→ Controlar
→ Entregar
Pregunta que responde este nivel: ¿Cómo ocurre este proceso de negocio de principio a fin?
Business Process = flujo real de negocio03
Nivel 3

Feature — la capacidad funcional que debe ofrecer el sistema

Una Feature es una capacidad funcional coherente y desarrollable. Empieza a traducir el proceso de negocio a producto de software.

No es una pantalla ni una tabla. Puede necesitar varias pantallas, servicios y validaciones para existir. Tampoco debería ser tan grande como “todo RMA”. Su tamaño ideal es el de una capacidad que pueda diseñarse, desarrollarse y probarse como una unidad con sentido.

Dentro de Reparaciones, por ejemplo, podemos imaginar Features como Alta de Orden, Gestión de Cola, Ejecución de Reparación, Control Técnico o Entrega. Cada una toma una parte coherente del Business Process y la convierte en una capacidad concreta del sistema.

Ejemplo
PROC-REP
├── FEAT-REP-001  Alta de Orden de Reparación
├── FEAT-REP-002  Diagnóstico y definición de reparación
├── FEAT-REP-003  Factibilidad y recursos
├── FEAT-REP-004  Gestión de cola de trabajo
├── FEAT-REP-005  Ejecución de reparación
└── FEAT-REP-006  Control técnico y entrega
Pregunta que responde este nivel: ¿Qué capacidad concreta debe ofrecer el sistema?
Feature ≠ pantalla · Feature = capacidad04
Nivel 4

User Story — qué necesita hacer un actor

La User Story expresa una necesidad desde la perspectiva de una persona o rol. Su foco no está en cómo se programa, sino en qué necesita lograr el actor y por qué eso le aporta valor.

Una Feature puede contener varias User Stories. Por ejemplo, “Alta de Orden de Reparación” puede incluir registrar al cliente, asociar el equipo, crear la orden y generar el comprobante de recepción.

La historia debe permanecer suficientemente cercana al lenguaje del usuario. Cuando empezamos a hablar de endpoints, tablas o funciones, ya estamos bajando a niveles técnicos posteriores.

Ejemplo
US-REP-001
Como recepcionista quiero registrar un cliente y su equipo
para poder iniciar una solicitud de reparación.

US-REP-002
Como recepcionista quiero crear una Orden de Reparación
para formalizar el ingreso del equipo al circuito RMA.
Pregunta que responde este nivel: ¿Qué necesita hacer el actor y qué valor obtiene?
User Story = necesidad del usuario05
Nivel 5

System Action — qué debe hacer concretamente el sistema

Las System Actions descomponen una User Story en acciones concretas que el sistema debe ejecutar para que esa historia sea posible.

Este nivel evita crear User Stories artificialmente pequeñas. Una historia puede seguir representando una necesidad completa del usuario, mientras que debajo se detallan las distintas acciones necesarias: validar datos, crear una orden, asignar un estado, registrar auditoría o asociar entidades.

Por eso una User Story normalmente tendrá varias System Actions, y una misma acción puede a su vez originar más de un requisito funcional.

Ejemplo
US-REP-002  Crear Orden de Reparación

ACC-REP-001  Validar datos necesarios
ACC-REP-002  Crear la Orden
ACC-REP-003  Asignar estado inicial REQUERIMIENTO
ACC-REP-004  Registrar usuario y fecha
ACC-REP-005  Relacionar la OR con el equipo
Pregunta que responde este nivel: ¿Qué acciones debe ejecutar el sistema para realizar la User Story?
System Action = acción concreta del sistema06
Nivel 6

Functional Requirement — el comportamiento verificable

El Functional Requirement transforma la necesidad en una afirmación precisa sobre cómo debe comportarse el sistema. Debe poder verificarse objetivamente.

Mientras la User Story dice “quiero crear una orden”, el requisito funcional puede decir que toda orden debe tener un identificador único, quedar asociada a un equipo, iniciar en un estado determinado y registrar quién la creó y cuándo.

Este nivel sigue hablando principalmente de comportamiento, no de tecnología. Todavía no debería definir si usamos PostgreSQL, FastAPI, UUID v4 o un endpoint específico, salvo que eso sea en sí mismo una restricción funcional acordada.

Ejemplo
FR-REP-001  Toda OR debe poseer un identificador único.
FR-REP-002  Toda OR debe quedar asociada a un equipo.
FR-REP-003  Toda OR nueva debe iniciar en REQUERIMIENTO.
FR-REP-004  Toda creación debe registrar usuario y fecha/hora.
Pregunta que responde este nivel: ¿Qué comportamiento verificable debe cumplir el sistema?
FR = contrato funcional07
Nivel 7

Technical Requirement — cómo debe resolverse técnicamente

El Technical Requirement es donde el diseño empieza a traducirse a arquitectura, datos, servicios, seguridad, APIs y decisiones de implementación.

Un requisito funcional puede necesitar varios requisitos técnicos. A la vez, un requisito técnico puede satisfacer varios requisitos funcionales. Por eso no queremos forzar relaciones uno a uno.

Si el requisito funcional dice que debemos registrar usuario y fecha de creación, el diseño técnico puede definir que el usuario se obtenga de la sesión autenticada y que la persistencia utilice campos como created_at y created_by. Ahí sí estamos especificando cómo debe construirse la solución.

Ejemplo
FR-REP-004
Toda creación debe registrar usuario y fecha/hora.

↓ puede requerir

TR-REP-002
El servicio debe obtener el usuario desde la sesión autenticada.

TR-REP-003
La persistencia debe almacenar created_at y created_by.
Pregunta que responde este nivel: ¿Qué decisiones y contratos técnicos hacen posible el comportamiento funcional?
TR = diseño técnico verificable08
Nivel 8

Task — la unidad concreta de trabajo de desarrollo

Una Task es algo que un desarrollador puede tomar y ejecutar. Es una unidad de trabajo concreta derivada de uno o más requisitos técnicos.

Por ejemplo, implementar un servicio puede requerir crear un modelo, una migración, un endpoint, validaciones y pruebas. Cada una de esas piezas puede ser una Task separada, aunque todas implementen el mismo Technical Requirement.

Este nivel es útil para planificar, estimar y repartir trabajo sin perder la relación con los niveles superiores. Una Task nunca debería existir aislada: idealmente siempre podremos navegar hacia atrás y entender qué requisito técnico, funcional, acción, historia y Feature está implementando.

Ejemplo
TASK-REP-001  Crear modelo RepairOrder
TASK-REP-002  Crear migration de repair_orders
TASK-REP-003  Implementar create_repair_order()
TASK-REP-004  Crear endpoint POST /repair-orders
TASK-REP-005  Agregar validaciones del request
Pregunta que responde este nivel: ¿Qué trabajo concreto tiene que realizar el equipo de desarrollo?
Task = trabajo ejecutable09
Nivel 9

Code / Artifact — qué produjo realmente la implementación

El nivel Code / Artifact representa el resultado concreto de una Task. Puede ser código fuente, una migration, un schema, una configuración, un componente de frontend o cualquier artefacto técnico relevante.

Preferimos hablar de “Code / Artifact” porque no todo lo implementado termina necesariamente en una función Python. Una Task puede producir un archivo SQL, una definición OpenAPI, un componente React, una migración o un archivo de configuración.

La trazabilidad ideal nos permitirá llegar desde un archivo o función hasta la razón de negocio que explica por qué existe.

Ejemplo
CODE-REP-001
backend/services/repair_orders.py
create_repair_order()

CODE-REP-002
backend/routes/repair_orders.py

CODE-REP-003
migrations/2026_09_create_repair_orders.sql
Pregunta que responde este nivel: ¿Qué artefacto concreto implementó la Task?
Code / Artifact = resultado técnico tangible10
Nivel 10

Internal Test — comprobar internamente que lo desarrollado funciona

El Internal Test verifica que la implementación cumple los requisitos funcionales y técnicos antes de exponerla a negocio.

Acá podemos tener pruebas unitarias, de integración o funcionales internas. Lo importante es que cada prueba pueda rastrearse hacia lo que está validando. Si un requisito dice que una OR nueva debe iniciar en REQUERIMIENTO, debería existir una prueba que compruebe exactamente eso.

El Internal Test responde a “¿lo construimos correctamente?”. Todavía no responde necesariamente a “¿esto resuelve el trabajo real del usuario?”. Esa segunda pregunta pertenece al UAT.

Ejemplo
TEST-REP-001
Crear OR válida → debe quedar en REQUERIMIENTO.

TEST-REP-002
Crear OR sin equipo → debe rechazarse.

TEST-REP-003
Crear OR → debe registrar usuario autenticado.
Pregunta que responde este nivel: ¿La implementación cumple técnicamente lo que definimos?
Internal Test = verificación interna11
Nivel 11

UAT — negocio confirma que realmente sirve

El User Acceptance Test valida que la funcionalidad funciona correctamente en términos de negocio y que puede utilizarse en la operación real.

Un test interno puede verificar que un endpoint devuelve 201 y guarda los datos correctos. En cambio, un UAT puede pedir que Recepción registre un cliente, seleccione el equipo, cree una OR y genere el comprobante esperado. El foco está en el resultado de negocio, no en los detalles internos de implementación.

Por eso Internal Test y UAT son niveles distintos. El primero protege la calidad técnica; el segundo protege la aceptación funcional.

Ejemplo
UAT-REP-001

Recepción registra un cliente,
selecciona su equipo,
crea la Orden de Reparación
y obtiene correctamente el comprobante de recepción.
Pregunta que responde este nivel: ¿Negocio confirma que la funcionalidad resuelve su necesidad?
UAT = aceptación funcional12
Nivel 12

Bug / Issue — qué pasa cuando algo no cumple

Un Bug / Issue aparece cuando una prueba interna, un UAT o la operación real detectan un desvío respecto de lo esperado.

La idea es que el bug no sea un ticket aislado. Debe quedar relacionado con el test o UAT que falló y, a través de esa relación, con el requisito funcional y la necesidad de negocio correspondiente.

Luego del fix, el ciclo vuelve a pruebas. De esta manera podemos saber no solo qué se corrigió, sino también qué parte del negocio estaba afectada y cómo se confirmó finalmente la solución.

Ejemplo
UAT-REP-001
↓ FAILED

BUG-REP-003
La OR de garantía no queda vinculada a la OR original.

↓ FIX
↓ RETEST
↓ UAT
↓ APPROVED
Pregunta que responde este nivel: ¿Qué desvío apareció y cómo cerramos el ciclo de corrección?
Bug = desvío trazable, no ticket aislado13
Agrupación opcional

Epic — una iniciativa transversal, no un reemplazo de Feature

El Epic no forma parte obligatoria de la cadena principal. Lo pensamos como una agrupación de planificación capaz de reunir varias Features, incluso de procesos distintos.

Esto es importante ahora que sabemos que RMA no tendrá solamente Reparaciones. Una iniciativa como “Gestión integral de repuestos” podría agrupar Features provenientes de Compras, Ventas y Reparaciones. En ese caso, el Epic atraviesa procesos y por eso no conviene colocarlo rígidamente entre Process y Feature.

El Domain y los Business Processes representan la estructura estable del negocio. El Epic, en cambio, puede aparecer y desaparecer según la planificación del proyecto.

Ejemplo transversal
EPIC-RMA-001  Gestión integral de repuestos
│
├── FEAT-COM-001  Crear órdenes de compra
├── FEAT-COM-004  Recepcionar repuestos
├── FEAT-VTA-001  Crear venta mayorista
└── FEAT-REP-005  Consumir repuestos en reparación
Idea clave: Epic agrupa iniciativas; Feature representa capacidades concretas del producto.
Epic = agrupación opcional y transversal14
Ejemplo completo

Cómo se ve la trazabilidad de punta a punta

Supongamos que queremos entender por qué existe la validación que impide a un técnico tomar una OR desde una estación no operativa. La trazabilidad nos permitirá recorrer la cadena completa desde negocio hasta implementación y pruebas.

Ejemplo E2E
DOM-RMA
↓
PROC-REP / PROC-REP-180
↓
FEAT-REP-004  Gestión de cola de trabajo
↓
US-REP-021    Como técnico quiero tomar una OR disponible
↓
ACC-REP-041   Validar sesión y estación
↓
FR-REP-052    La estación debe estar operativa
↓
TR-REP-073    Validación técnica de estación
↓
TASK-REP-103  Implementar validación
↓
CODE-REP-...
↓
TEST-REP-...
↓
UAT-REP-...
↓
APPROVED

La misma cadena podrá recorrerse al revés. Desde una función o endpoint podremos entender qué Task lo creó, qué requisito técnico implementa, qué comportamiento funcional cubre, qué necesidad de usuario satisface y en qué proceso de negocio se origina.

Objetivo final: poder responder tanto “¿qué código implementa esta regla de negocio?” como “¿por qué existe este código?” sin perder el contexto.
